# 전환 비용 측정 프로토콜 v2

작성 2026-11-23. 이 문서는 측정을 시작하기 전에 고정한다. 실행 중에 바꾸는 것은 맨 끝 "변경 기록"에 날짜와 이유를 남긴다.

## 1. 질문

Small로 추적하다가 프레임 s에서 Base+로 바꿀 때, Base+가 s+1을 처리할 준비를 마치기까지 방법마다 시간과 GPU 메모리가 얼마나 드는가. 정확도 비교(README 3장)와 같은 case와 같은 방법을 쓴다. 그래서 정확도와 비용을 한 표에 나란히 놓을 수 있다.

이 측정은 기술 통계다. 미리 정한 가설 검정은 없다. 보고서에 쓸 주된 비교는 다음 두 가지다.

- **C1.** 메모리를 넘기는 방법(재개, translator 두 종류)과 프롬프트 재시작(5종)의 전환 1회 준비 시간 비율.
- **C2.** 같은 비교를 프레임 단위로 바꾼 값. 전환 비용을 "Base+ 한 프레임 처리 시간의 몇 배"로 나타낸다.

## 2. 대상: 테스트 세트 전체

학습 데이터와 장면이 겹치지 않는 두 세트를 쓴다(MOSE dev와 LVOS val은 학습 장면과 겹쳐서 뺀다).

| 세트 | 영상 | 객체 | 전환 지점 | 전환 수 |
|---|---:|---:|---|---:|
| PUMaVOS | 전체 24 | 26 | 25 / 50 / 75% | 78 |
| M3-VOS | `ImageSets/val.txt` 전체 471 | 530 | 50% | 530 |

- **전환 프레임.** 객체가 처음 보이는 프레임을 start, 마지막으로 보이는 프레임을 end라 할 때, s = min(max(start + round(f·(end − start)), start + 1), end − 1)이다. 정확도 실행과 같은 식이다.
- **M3-VOS 범위.** 정확도 실행은 val의 앞 81 영상만 썼다. 비용은 val 전체를 잰다. 앞 81 영상의 110 전환은 정확도 결과와 짝지을 수 있고(G2 검사도 이 전환에서 한다), 세트별 표에는 "앞 81 영상"과 "전체"를 함께 적는다.

## 3. 방법

| 이름 | 추적 모델 (s까지) | Base+가 받는 것 |
|---|---|---|
| `resume` | Base+ | Base+ 자신의 메모리 상태 |
| `paper` | Small | Small 상태를 논문 translator(r2 epoch 26)로 변환한 것 |
| `conv_strip_vm` | Small | Small 상태를 학습 없는 선형 변환으로 바꾼 것 |
| `restart_p0` | Base+ | 처음 프롬프트(P0 프레임 + GT 마스크) |
| `restart_mask` | Base+ | Base+가 s까지 마지막으로 보인다고 판단한 프레임과 그 마스크 |
| `restart_p0_mask` | Base+ | P0 + Base+의 마지막 마스크 |
| `olv` | Small | P0 + Small의 마지막 마스크(논문 기준선) |
| `lastvis` | Small | Small의 마지막 마스크 |

- `resume`은 실제 시스템에서는 없는 상황이다. Base+가 처음부터 돌았다고 가정한 상한선이다.
- `restart_p0`, `restart_mask`, `restart_p0_mask`도 Base+ 자신의 마지막 마스크를 쓰므로 같은 가정이다.
- `paper`, `conv_strip_vm`, `olv`, `lastvis`는 실제 전환 상황, 즉 Small만 돌고 있던 상황이다.
- "마지막으로 보인다고 판단한 프레임"은 object score가 0보다 크고 마스크가 비어 있지 않은 마지막 프레임이다. 정확도 실행과 같은 규칙이다.

## 4. 측정 구간

**시작:** s까지 추적한 tracker가 원래 SAM2 inference state를 GPU 메모리에 들고 있는 시점이다. 아무것도 내보내지 않았다.

**끝:** 새로 만든 Base+ 세션이 s+1을 처리할 준비를 마친 시점이다. SAM2 `propagate_in_video_preflight`가 끝난 뒤다.

| 방법 | 구간 안에서 하는 일 (차례대로, 단계별로도 잰다) |
|---|---|
| 메모리 방법 | ① 상태 내보내기(canonical 형식, GPU→CPU) ② 변환(translator만, CPU→GPU→CPU 포함) ③ Base+ 세션에 주입 ④ preflight |
| 재시작 방법 | 프롬프트마다 ① 저장된 JPEG 읽기·디코딩·리사이즈 ② `add_new_mask`(Base+ 이미지 인코더 포함) → 끝에 ③ preflight |

구간에 넣지 않는 것:
- s까지의 추적
- 모델 불러오기, 프로세스 시작
- s+1 프레임의 디코딩과 인코딩(모든 방법에 똑같이 들어간다)

시계는 `torch.cuda.synchronize()` 사이에 둔 `time.perf_counter()`다. 그래서 각 값은 CPU 작업, GPU 작업, 전송을 모두 포함한 실제 경과 시간이다. 단계별 시간도 같은 방식으로 따로 재며, 단계 합은 전체와 거의 같아야 한다(차이는 Python 호출 비용).

정밀도: bf16 autocast는 정확도 실행과 같다. 내보내기와 변환은 정확도 실행처럼 autocast를 끈 상태에서 한다.

## 5. 반복과 대표값

- 전환마다 첫 호출 1회를 따로 기록한다(cold). 이어서 버리는 호출 3회(warm-up), 재는 호출 20회를 한다. 20회의 원시값은 모두 저장한다.
- 전환별 대표값은 20회의 중앙값이다.
- 세트별 값은 전환별 대표값의 중앙값과 사분위 범위(IQR), 95백분위수다.
- **신뢰구간.** 영상 단위 bootstrap 95%(10,000회, 영상을 복원추출해 그 영상의 전환을 모두 넣음)로 세트별 중앙값과 C1 비율의 구간을 낸다. 합친 값은 두 세트를 같은 가중치로 평균한다. 정확도 표와 같은 관례다.
- **C1 비율.** 전환마다 (재시작 방법 시간) / (메모리 방법 시간)을 구하고, 그 중앙값을 보고한다.
- **C2.** 각 tracker 프로세스에서 추적 한 단계의 시간을 잰다(처음 10단계 제외, case별 중앙값). 전환 비용을 Base+ 한 프레임 시간으로 나눈다.
- **첫 호출.** 프로세스의 첫 전환과 나머지를 나눠서 보고한다. 첫 전환의 cold 값은 커널 초기화가 섞인다.

## 6. 메모리와 데이터 크기

- **GPU 메모리.** 시작 시점 대비 최대 추가 할당량(`max_memory_allocated`)과 최대 추가 예약량(`max_memory_reserved`)이다. 첫 호출, warm-up, 반복을 모두 포함한 최대값이다.
- **넘기는 데이터.** 메모리 방법은 canonical 상태 중 유효 기록의 바이트 수다. 재시작은 프롬프트 JPEG 파일 크기와 1비트 마스크(H·W/8 바이트)의 합이다.

## 7. 실행 조건

- **하드웨어와 환경.** RTX 4080 SUPER(GPU 0) 한 장, torch 2.8, SAM2.1 체크포인트를 쓴다. 정확도 실행과 같은 환경이며 버전은 결과 파일에 기록한다.
- **실행 방식.** 방법 하나당 프로세스 하나를 차례로 돌린다. 한 번에 측정 프로세스는 하나뿐이다. 순서는 resume, paper, conv_strip_vm, restart_p0, restart_mask, restart_p0_mask, olv, lastvis다.
- **GPU 1.** 측정 중에는 GPU 1도 쓰지 않는다. CPU 디코딩 시간이 다른 작업에 흔들리지 않게 하기 위해서다.
- **GPU 클럭.** 고정하지 않는다. 시스템 설정 변경이 필요해서다. 대신 클럭, 온도, 전력을 전환마다 기록하고, 고정 작업으로 드리프트를 감시한다(G4).

## 8. 검사 (보고 전에 모두 통과해야 함)

| 검사 | 기준 | 실패하면 |
|---|---|---|
| **G1 GPU 단독 사용** | 전환마다 측정 직전과 직후에 GPU 0의 compute 프로세스가 자기 자신뿐 | 그 전환을 지우고 다시 잰다 |
| **G2 같은 경로** | 시간을 잰 경로로 만든 세션을 s+1까지 돌린 예측 면적이, 정확도 실행의 s+1 예측 면적과 같다. 정확도 실행에 있는 전환(PUMaVOS 78, M3-VOS 앞 81 영상 110)에서 s+1 예측 마스크의 픽셀 수가 정확히 같다(정확도 실행에 저장된 면적 × H·W를 반올림한 값과 비교) | 원인을 찾을 때까지 보고하지 않는다. 일부 방법만 실패하면 그 방법을 표에서 빼고 사유를 적는다 |
| **G3 완전성** | 모든 방법이 2장의 전환을 빠짐없이 가진다 | 빠진 전환만 다시 잰다(스크립트가 끝난 전환을 건너뜀) |
| **G4 드리프트** | 고정 작업(Base+ 이미지 인코더, 고정 입력, 20회 중앙값)을 프로세스 시작, 25 전환마다, 끝에 잰다. 모든 값이 그 프로세스 시작값의 ±5% 안 | 벗어난 구간을 표시하고, 그 구간 전환을 다시 잰다 |
| **G5 반복 안정성** | 전환별 20회의 IQR/중앙값을 기록한다 | 0.1을 넘는 전환의 비율을 보고한다(제외하지 않음) |
| **G6 이전 값 재현** | 스모크 4 case의 50% 전환 중앙값이 6 case 측정(`checks/single/`)의 같은 case와 ±10% 안 | 차이 원인을 적는다 |

**G2 주의.** 정확도 실행은 `sources.resolve`를 (Small 상태, Base+ 상태) 쌍으로 불렀다. 비용 측정에서는 Base+ 상태가 없는 실제 상황처럼 (Small, Small)로 부른다. translator가 Base+ 상태를 쓰지 않는다면 G2가 통과한다. 실패하면 정확도 실행의 translator 값이 실제 시스템에서 얻을 수 없는 정보를 썼다는 뜻이므로 따로 보고한다.

## 9. 실행 순서

1. **스모크.** `--smoke`로 4 case(PUMaVOS billie_hair, caps / M3-VOS 0001_open_cup_1, 0004_open_cup_6), 8개 방법을 모두 돌린다. G1, G2, G4, G6을 확인한다. 하나라도 실패하면 본 실행을 시작하지 않는다.
2. **본 실행.** `./cost_v2.sh`로 8개 방법을 차례로 돌린다. 출력은 `checks/v2/<방법>.json`, 로그는 `logs/cost_v2_<방법>.log`다. 중간에 끊기면 같은 명령으로 이어서 돌린다.
3. **감독.** 하위 세션이 10분마다 진행, 오류, G1 위반을 확인한다. 멈춘 방법은 이어서 다시 시작한다.
4. **정리.** `code/summarize_cost_v2.py`가 G1–G6 판정과 표를 `cost_v2_summary.md`, `cost_v2_summary.json`으로 낸다.

## 10. 보고할 표

1. 방법별·세트별 준비 시간: 중앙값 [95% CI], IQR, p95. 최대 추가 메모리. 넘기는 데이터.
2. 단계별 중앙값.
3. C1 비율: 메모리 방법 3종 × 재시작 5종, 세트별과 합친 값, [95% CI].
4. C2: 프레임 수로 환산한 전환 비용. Base+와 Small의 한 프레임 시간.
5. 첫 호출(프로세스 첫 전환과 나머지).
6. 전환 지점(25/50/75%)별 중앙값(PUMaVOS).
7. 정확도 표(README 3.1)와 나란히 놓은 표(M3-VOS 앞 81 영상과 PUMaVOS).
8. 검사 결과 G1–G6.

## 11. 알려진 한계

- GPU 한 종류(RTX 4080 SUPER)에서만 잰다.
- 클럭을 고정하지 않는다(G4로 감시만 한다).
- 재시작의 JPEG 디코딩은 디스크 캐시 상태에 따라 달라질 수 있다. 같은 파일을 24번 읽으므로 반복 측정은 OS 페이지 캐시에 올라간 상태를 잰다. 첫 호출에는 디스크 읽기가 섞일 수 있다.
- 두 프롬프트 재시작의 preflight가 한 프롬프트 재시작보다 훨씬 긴 이유(시험 측정에서 38 ms 대 1.1 ms)는 아직 추적하지 않았다. 측정값은 그대로 보고하고 원인은 한계에 적는다.

## 변경 기록

- **2026-11-23, 스모크 전.** M3-VOS val의 영상·객체 수(2장 표)는 미리 세지 않았다. 마스크를 모두 읽어야 해서 너무 오래 걸렸다. 본 실행 결과에서 채웠다: 471 영상, 530 객체, 530 전환(합계 608). 실행 환경도 기록해 둔다: CPU Intel Core Ultra 7 270K Plus, 컨테이너에 4코어. 드라이버 595.99, torch 2.8.0+cu128.
- **2026-11-23, 스모크 1차.** 넘기는 데이터 크기를 세는 코드가 시간을 재는 구간 안에 있었다(+0.3–0.4 ms). 구간 밖으로 옮기고 스모크를 처음부터 다시 돌렸다.
- **2026-11-23, 스모크 2차 결과.** G1, G2(8개 방법 × 8 전환 모두 픽셀 수 일치), G3, G4(최대 1.6%)는 통과했다. G6은 `paper` billie_hair 하나만 38.6% 차이가 났다. 기준값 쪽이 이상값이다. 6 case 측정은 warm-up 없이 첫 호출 뒤 바로 10회를 쟀다. 그래서 프로세스 첫 case의 내보내기가 3.07 ms(다른 case는 1.3 ms)로 부풀어 있었다. 나머지 case는 모두 9% 안에서 일치한다. 본 실행을 시작한다.
